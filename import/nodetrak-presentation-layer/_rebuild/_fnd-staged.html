Reading sample

Instrumenting a freshness metric
Freshness measures the share of pipelines that refreshed on schedule. It is the first metric a new data team should govern, because every downstream number inherits its failures.
Compute it per pipeline as on_time_runs / scheduled_runs over a trailing window, then aggregate by source system. Runs that never started count as late: silence is the worst kind of failure.
4px base. Reading columns cap at 70ch; page content caps at 1060px. Section rhythm is generous: 96px between major sections, 28px between sibling modules. Breathing floors (R8): module padding ≥24 · label→content ≥10 · tile gaps ≥16 · column gaps ≥28 · sibling surfaces ≥16 apart.

A collapsible section header keeps long reference pages scannable. The chevron, anchor link, and optional action live on the header row; the intro paragraph and body collapse together.
Open layout: a labelled chip, then text. The chip carries the tint and the body sits in the reading flow, so a callout interrupts without breaking the column. The boxed summary variant is the one exception.
NoteFreshness targets differ by tier: hourly pipelines target 99%, daily pipelines 95%.
TipAlert on the trend, not the level. Three consecutive drops beat any single threshold.
ImportantFreshness is a prerequisite metric: report it before any quality or usage number.
WarningNever average a ratio metric across segments. Recompute from raw counts.
RequirementEvery published metric must name an owner and a data source. REQ-04
Exampleevents_core: 412 of 437 scheduled runs on time → 94.3% freshness.
LimitationFreshness says nothing about correctness: a broken pipeline can be perfectly punctual.
CorrectionThe 94.3% published on 12 Aug counted two backfilled runs as on time. The corrected value is 93.9%.

Summary

Define the metric from raw counts, set tier-specific targets, alert on trends, and publish only with an owner attached. Everything else in this guide is elaboration.

Use case Method · Funnel analysis
Prioritizing UX debt on a checkout flow
Context Growth PM at a mid-market retailer; two-week window before the seasonal freeze. Problem Twelve known UX issues, budget to fix three, no shared basis for choosing. Application Mapped each issue to its funnel step, weighted by step traffic × drop-off contribution. The slot fill marks an empty zone waiting for real material, and is the only place a grey field is allowed to stand in for content. Captions are mono and sit under the frame; the title and the one-line description sit above it, so a reader knows what they are about to look at.
Code is a domain component, not a media type: it carries a filename, a language, and syntax that a reader parses token by token. The surface is white like every other reading surface, and hue is admitted here and nowhere else in the system.

SQL
-- share of tables inside their freshness SLA
select
count_if(now() - max_loaded_at <= sla_hours) as fresh_tables,
count(*) as sla_tracked_tables,
round(100 * fresh_tables / sla_tracked_tables, 1) as freshness_pct
from analytics.meta.table_freshness
where sla_hours is not null and tier = 'daily'

Extension points

Where an implementation is expected to add its own material without adding chrome. Everything named here is data the system reads, not a fixed scheme.
The semantic set (ok, warn, crit, info, note) is remappable. Labels are data; the five tints and their pairings are design.
Scales assume no fixed level count. Difficulty dots, score segments and progress steps all render from the data they are given.
Dark mode is deferred, and the polarity rules (black text on light, white text on black) are written to invert cleanly when it lands.
Content fields follow the source schemas. New fields inherit an existing row, pair or chip; a new field never earns new chrome.
