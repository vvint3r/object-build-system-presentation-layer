A method binds objective, applicability, steps, and decision criteria into one card: shown in the emphasized container variant (black border, soft black offset) for when a module must pop without claiming the reserved teal. Sample: backfill validation.
Method Backfill validation ●●○ · 30–60 min per pipeline
Objective
Prove a backfilled window is statistically indistinguishable from live-computed history.
When to use
After any schema change, replay, or incident fix that rewrote history.
Prerequisites
Run logsSnapshot table
RiskSampling too few partitions hides drift at month boundaries.
Steps
01Pick 5 partitions spanning the backfilled window, including both edges.
02Recompute the metric from raw counts in each partition.
03Diff against the snapshot table; log deltas per partition.
04Attach the diff memo to the registry entry.
DecisionAny delta > 0.5%? → reject the backfill and open an incident; else approve.

Card layout for tradeoff reading; the recommended option carries the reserved treatment. The table variant lives in Foundations ss: 11.
Option A

Threshold alerts

Fire when the level crosses a fixed line.
+Trivial to set up and explain
−Noisy near the line; misses slow drift
Best for
SLA contracts
Option BRecommended

Trend alerts

Fire on consecutive drops, regardless of level.
+Low false-alarm rate; catches drift early
−Slower to fire on sudden total failure
Best for
Most teams
Option C

Anomaly detection

Model the expected series; alert on deviation.
+Adapts to seasonality automatically
−Opaque; needs tuning and history
Best for
High-scale platforms
SelectionStart with B; add A only where a contract names a number; add C when B's window tuning stops scaling.
