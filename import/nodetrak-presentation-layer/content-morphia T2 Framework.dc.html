A structured way to choose user-experience metrics: five quality dimensions, each traced from a goal to an observable signal to a measurable metric.
Framework UX measurement Intermediate ~15 min · updated Jul 2026

Overview

Teams default to what is easy to count — sessions, clicks, DAU — and end up optimizing motion instead of quality. HEART forces the order of operations: name the quality goal first, find a signal a user actually emits, and only then define the metric. Use it when a team ships UI changes and cannot say whether experience improved.

Read each column top to bottom. A metric with no signal above it is vanity; a goal with no metric below it is a wish.

When to use it

Use when
Scoring a UI or flow change where "better" is contested
Choosing success metrics before an A/B test
Auditing a dashboard full of motion metrics
Not for
Business-model metrics — revenue, margin, CAC
Infrastructure quality — latency, uptime
Anything you will not act on — five dimensions ≠ five obligations

Implementation

1Pick 2–3 dimensions that match the product goal. A queue redesign cares about Engagement and Task success, not Adoption.
2Write the goal in the user's words. "I can queue songs without leaving the player" — not "increase queue usage".
3Confirm each signal is instrumented. If the event does not exist, the metric goes on the roadmap, not the dashboard.
4Set a target and an owner per metric. A HEART table without owners decays into wall art in one quarter.

Worked example

Example 01 Music-streaming queue redesign
Scenario: the team rebuilt the play-queue UI and needed to know whether the experience improved, not just whether people touched it.
Input · dimensions chosen
E → queue edits / session
T → add-to-queue success %
H → in-app pulse survey
Output · after 4 weeks
edits +18% · success 94→98%
pulse +0.4 (5-pt scale)
decision: SHIP + follow-up
Key takeaway
Three dimensions were enough — the discipline is in what you decline to measure.

Limitations

Limitation
HEART tells you what to measure, not what to build. It assumes the product direction is right and scores execution quality. Pair it with a prioritization framework when direction itself is in question.
Note
Happiness metrics lag. Survey-based signals move weeks after the behavior metrics do — read them on a longer window.
